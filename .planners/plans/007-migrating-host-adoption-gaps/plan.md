# Close the gaps a migrating host hits on adoption

## Plan

Reviewing the first real adoption — `planners`, the package this library was
extracted from, moving onto the published `pkgskills` — turned up three gaps
that are not specific to that host. Any package that migrates from a home-grown
install layer hits the first two; every dispatcher host hits the third.

### 1. Name a pre-pkgskills stamp for what it is

A host that stamped its files before adopting pkgskills used the same
`<!-- generated by <dist> ` prefix (that is where the prefix came from), minus
the `via pkgskills` token. Today `classify` handles that file like this:

- `is_stamped` is false, because `_line_re` requires the token.
- `stamped_by` matches `_ANY_RE`, which only needs the prefix, and returns the
  host's own dist.
- The verdict is `foreign` with reason `generated by <dist>, not <dist>`.

The status is right: `--force` is the remedy, and a wholesale rewrite is what
the user wants. The reason is nonsense. Split the case in `classify`: when
`stamped_by` returns the host's own dist and `is_stamped` is false, report
`foreign` with `stamped by an earlier <dist> release, before pkgskills; --force
replaces it`. Leave the true-foreign message (`generated by <other>, not
<dist>`) for a different dist.

`stamped_by` itself stays as is. The distinction belongs in `classify`, which is
where the two predicates meet; the helper's contract ("the dist named in the
stamp line") is still correct.

Add a row to `test_foreign_shapes` covering a same-dist stamp without the
token, and one asserting the different-dist message is unchanged.

### 2. Carry `force` in `InstallReport`

`--force` is a pkgskills flag, but `after_install` receives an `InstallReport`
of `host`, `mode`, `root`, `written`, `removed`, and `shadowed`. The user's
explicit consent to overwrite never reaches the host. A host hook that edits a
file in place rather than rewriting it wholesale — the motivating case is a
line appended to `.gitattributes` — has no way to know whether a differing
line may be replaced, so it either always refuses or always clobbers.

Add `force: bool = False` to `InstallReport`, populated by `install` from its
own argument. Document it on the dataclass and in the `after_install` bullet
of the `Host` docstring: the hook honors `force` for anything it edits in
place, and a hook that only creates files may ignore it.

This is deliberately the whole change. The wider question — host-declared
install options such as a "skip the hook" or "also install the tool"
switch — is a design decision about whether `after_install` side effects
should be opt-in or opt-out, and it changes the CLI surface. Record it in the
Log as an open question and take it up only if a second host asks for it; one
host's flags are not yet a pattern.

### 3. Bare `skill` on a dispatcher host lists the bodies

`<cli> skill` with no name errors when the host ships more than one body and
tells the user to pass `--list`. Listing is the only thing a bare invocation
can usefully mean on a dispatcher host, and it is what the first host did
before adopting. Make the no-name, many-bodies case behave as `--list`;
the single-body case keeps printing that body. `--list` stays as the explicit
form.

Update the `skill` command help and the test in `test_cli.py` that asserts the
error, and check `assert_prompt_commands` still accepts a bare `<cli> skill`
mention in a prompt body.

### Implementation order

1. `classify` message split, with tests.
2. `InstallReport.force`, threaded from `install`, with a test that a hook
   sees the flag both ways.
3. `skill` bare-invocation listing, with tests and help text.
4. Changelog entries under `[Unreleased]`: one Fixed (the message), two Changed
   (the report field, the listing). The report field is additive and the
   listing replaces an error, so no host breaks; say so.

### Out of scope

Host-declared install options (see section 2), and any change to the stamp
format itself. A pre-pkgskills stamp stays `foreign`; only its reason changes.
